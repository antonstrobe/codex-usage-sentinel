# Управление через Telegram

Серверная версия работает круглосуточно без Windows-программы. Откройте своего бота и отправьте `/start` или `/menu`. Питер и другие заранее разрешённые участники используют те же кнопки; устанавливать EXE не требуется.

- **Будильники** → событие: процент, количество сообщений, интервал, повтор до восстановления, включение и удаление. Новое событие создаётся выключенным. Можно выбрать готовое число или ответить на запрос своим числом.
- **Пауза**: 15 минут, час, 8 часов, до ручного включения; тихий статус продолжает обновляться.
- **Тестовое сообщение**: один или десять звуковых тестов, остановка теста.
- **В группу / Лично владельцу**: выбирает единственного получателя. Переключатель действует для всего монитора, а личный чат — это сохранённый чат владельца.
- **Тихий статус**: одно сообщение вида `34%`. После звукового сообщения публикуется новый тихий статус ниже него, предыдущий статус удаляется. Кнопка «Управление» под процентом открывает отдельное меню.
- **Источник лимитов** или `/status`: точное название квоты, окна, сбросы и фактическая модель CLI. **Обновить лимиты** запрашивает новое чтение, не чаще раза в 10 секунд. Обычно опрос идёт каждую минуту.

Активные переключатели зелёные и с галочкой. Telegram задаёт оформление и не предоставляет подсказки при наведении для таких кнопок. Подписи показывают текущее состояние. Звук зависит от настроек клиента Telegram и телефона.

## Astra · Ultra и точность данных

Источник использует существующий профиль авторизации CLI WeChat, проверяя его совпадение с работающей службой. Он вызывает только `initialize`, `model/list`, `account/rateLimits/read`; не создаёт задачи модели, не оплачивает и не применяет сбросы. Авторизация не копируется в бота.

Если сервер отдаёт одну квоту с названием Astra, выбирается она. Иначе отображается общий `codex` с явной подписью «общий лимит аккаунта». Квота другой модели (например Spark) не подставляется. Отдельный счётчик для уровня reasoning Ultra не предполагается. Наличие Astra проверяется через список моделей; отсутствие показывается в меню источника. Будильники используют наименьший остаток окон выбранной квоты, а не вымышленный отдельный процент Ultra.

При отсутствии свежих данных показывается `—%`, звуковые будильники ждут успешного чтения. Неизменный процент не вызывает повторной отправки. При выключенном сервере последнее сообщение остаётся в чате без обновления.

Схемы: [Codex App Server](https://learn.chatgpt.com/docs/app-server), [Telegram Bot API](https://core.telegram.org/bots/api).

## Развёртывание оператором / Codex

1. Проверьте существующий CLI, его профиль и службы WeChat. Не меняйте авторизацию, модель или конфигурацию рабочего WeChat. Проверьте `getWebhookInfo`: если webhook уже занят, остановите установку и разберитесь с существующим получателем. Не используйте второй `getUpdates` параллельно.
2. Выполните `python3 -B -m unittest server.test_server -v`. Разместите исходники в отдельном выпуске `/opt/codex-usage-sentinel/releases/...`; `current` указывает на проверенный выпуск. На сервере нужны Python 3.10+ и systemd с зашифрованными credentials. Сторонние Python-пакеты не нужны.
3. Создайте группу `codex-usage` и системного пользователя `codex-usage-bot` без оболочки входа. Шаблон `codex-usage-source.service` работает от существующего пользователя CLI; исправьте пути и имя службы под своё окружение. У бота отдельный пользователь, которому недоступна директория авторизации Codex.
4. Скопируйте `server/config.example.json` в `/etc/codex-usage-bot/config.json`; задайте реальные ID только на сервере, файл `root:codex-usage`, `0640`. Числовой ID владельца должен быть в `allowed_users`. `pending_usernames` — необязательная одноразовая привязка заранее разрешённого имени: пользователь должен состоять в заданной группе; после первого обращения закрепляется числовой ID.
5. Получите токен через локальное защищённое хранилище или интерактивный секретный ввод. Через stdin передайте его `systemd-creds encrypt --name=telegram-token - /etc/credstore.encrypted/codex-usage-bot.cred`. Никогда не помещайте токен в командную строку, исходники, обычный файл или журнал. Каталог зашифрованных credentials принадлежит root; файл `0600`.
6. Перенесите выбранного получателя, будильники, паузу и известные ID сообщений статуса из старой установки в `/var/lib/codex-usage-bot/state.json`. Старый локальный монитор остановите перед включением отправок на сервере. Источник теперь серверный аккаунт CLI; локальные срабатывания от другого источника не переносятся как текущие.
7. Установите только два новых unit-файла из `server/`; `systemctl daemon-reload`, затем `systemctl enable --now codex-usage-source codex-usage-bot`. Nginx, VPN, сайт и службы WeChat перезапускать не требуется. Бот использует исходящие HTTPS-запросы; входящих портов нет.
8. Проверьте `systemctl is-active codex-usage-source codex-usage-bot`, свежесть `/var/lib/codex-usage-source/snapshot.json`, `/var/lib/codex-usage-bot/health.json`, и реальные сообщения в разрешённом чате. Конфигурацию, состояние и credentials в Git не добавляйте. Для остановки только этого монитора: `systemctl disable --now codex-usage-bot codex-usage-source`.

Сервер хранит ID статуса и очереди между перезапусками. Неопределённый результат отправки звукового сообщения не повторяется автоматически: возможен пропуск одного уведомления, но не бесконечный дубль. Неопределённое создание статуса требует кнопки восстановления; неизвестное старое сообщение может остаться. Ответ `429` учитывает `retry_after`. Между запросами записи минимум 2 секунды; групповые отправки дополнительно разнесены минимум на 3,1 секунды. Перенос тихого статуса увеличивает фактический интервал между будильниками.

Не запускайте одновременно старый Windows-монитор с тем же ботом и тем же чатом. После переноса оператор может создать рядом с `start.ps1` локальный `server-mode.json` с `{"enabled":true}`, чтобы штатный launcher больше не запускал локальные отправки.
